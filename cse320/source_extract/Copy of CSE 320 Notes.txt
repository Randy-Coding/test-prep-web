P77: Principle of Locality
P79: Principle of Locality: Programs like to use data and instructions with addresses near or equal to those used recently
P80: Temporal locality: Recently referenced things are likely to be referenced again in the near future
P81: Spatial locality: Items with nearby addresses tend to be referenced close together in time
P82: These are true because of a cache (we will learn about this soon)
P86: In this example, doing a[i][j] is better than a[j][i] because if you do a[j][i], then you jump around a lot because a[i] moves by N ints after each iteration (not spatially local)

P121: Disk (HDD)
P122: The disk:
P125: Disks consist of platters. They have 2 surfaces: Top and bottom
P126: The arm has heads that reach every single surface
P127: Damaged platters are managed accordingly by other hardwares
P128: Each surface has tracks (like track and field lanes)
P129: Each track is divided into sectors (there are gaps between sectors)
P130: Outer tracks have more sectors than inner tracks
P131: Aligned tracks form a cylinder (not useful for upcoming calculations)
P133: Capacity: Number of bytes that can be stored. Determined by:
P134: Recording density (bits/in): # of bits squeezed into a 1 inch segment of a track
P135: Track density (tracks/in): # of tracks that can be squeezed into a 1 inch radial segment
P136: Areal density (bits/in2): Product of recording and track densities
P137: (# bytes/sector) * (avg # sectors/track) * (# tracks/surface) * (# surfaces/platter) * (# platters/disk)
P139: Read from disk:
P140: Seek: Move the arm to the correct track
P141: Rotation: Let the platter spin to the correct sector (very slow)
P142: Transfer: Let the platter spin while the arm reads
P143: Access time = Seek + Rotation + Transfer
P147: Average rotation time = ½  * (1/RPM) * (60 sec/ 1 min)
P148: Average transfer time = (1/RPM) * 1/(avg # sectors/track) * (60 secs/1 min)
P150: There’s a mapping between logical blocks and physical sectors. CPU looks at logical blocks and then the disk moves to the corresponding sector. CPU does not control the disk
P159: I/O Bus
P162: DMA bulk copies data to/from main memory to the disk. Like memcpy
P163: The CPU does not have to do any of this
P164: IRQ: Works like an alarm. Basically the CPU is minding its own business when an I/O event (like mouse click) occurs and sends the interrupt signal to the CPU. Then the CPU will figure out what it’s retrieving from the I/O bus and act accordingly
P165: Polling: CPU consciously and consistently checks for interrupt. Useful for GeoDash
P167: Solid State Disk (SSD)
P171: Blocks wear out after ~100,000 writes. Afterwards, they can only be read, not written to
P172: Data is read/written in whole pages
P173: Pages can only be written to once its block is erased
P174: Sequential access is faster than random access
P175: Random writes are somewhat slower
P176: Erasing a block takes a long time (~1 ms)
P177: Modifying a block page requires all other pages to be copied to new block
P179: SSDs have no moving parts. Faster than HDDs and actually consume less power (because no moving parts). However, they wear out and are more costly ($).
P180: Caches
P183: Caches exist between the CPU and RAM
P184: Hits (cache has it)
P185: Misses (cache doesn’t have it. Then...)
P186: Placement policy (where does new block go)
P187: Replacement policy (which block gets evicted)
P190: Types of cache misses:
P191: Cold miss: Cache block is empty (valid = 0)
P192: Conflict miss: In the above diagram, 10 and 14 can only be stored in that same block. Calling 10, 11 is fine, but 10, 14, 10, 14 is bad (engineer’s duty)
P193: Capacity miss: There are more active cache blocks than the cache (programmer’s duty)
P195: Mapping RAM to cache:
P196: Extreme 1: Directly mapped (the 10 14 example). Lines = 1
P197: Extreme 2: Fully Associative: RAM blocks can go anywhere in cache. Sets = 1
P198: Middle ground: Set-associative: Every address in RAM has 1 cache set that it can use. However, it can use any line within said set
P203: Cache layout (regardless of mapping):
P204: There are S sets
P205: Each set contains E lines
P206: Each line contains a valid bit, a tag, and a block B that holds the actual data
P207: S, E, and the number of bytes within B are all powers of 2
P209: When an instruction accesses data from main memory, it first checks if it exists in the cache. The address of said data is split into: Tag, index, offset
P210: Use index to locate the corresponding set
P211: Go through all lines in said set
P212: If a line’s tag matches the address’ tag AND the valid bit = 1, then cache hit. We take the data from the line’s block (0 + offset)
P213: The valid bit is 0 upon machine startup and is permanently 1 once the line gets placed
P217: Upon a cache miss, data is read from RAM as follows: [tag | set | # of bytes]
P218: The # of bytes asked is the same as the size of the cache blocks
P219: Reading a single byte from RAM is a waste of time. Why not read to the whole block?
P221: Example using matrix multiplication: SLIDES
P222: By rearranging the i, j and k loops and traversing the matrices differently, we can use more spatial locality
P223: But the “standard” matrix multiplication requires traversing each element n times
P224: So we divide the matrices into submatrices so they fit into the cache once, multiply submatrices, place them in matrix C, evict them and never use them again
P225: Writes
P227: If I write to cache, when do I actually push it to RAM?
P228: Write-through (immediately write back to memory). Problem: Slow
P229: Write-back (wait until line gets evicted). Problem: Multiple cores working on the same address
P230: Requires a dirty bit (“This block has been modified and must be written back”)
P232: How about a write-miss? 2 options:
P233: Write straight to memory, skip the cache. OR
P234: Write-allocate (load into cache, update line in cache). Good if there will be more writes to this location
P236: Typical implementations:
P237: Write-through straight to memory
P238: Write-back and write-allocate
P240: Hit and Miss Metrics
P242: Miss rate and hit rate
P243: Hit time: Time to deliver a line in the cache to the processor. Includes time determining whether line is in the cache. Very fast
P244: Miss penalty: Very slow. Can take hundreds of cycles to access from RAM
P246: How bad is a cache miss? Consider a 97% and 99% hit rate. Assume:
P247: Hit time: 1 cycle
P248: Miss penalty: 100 cycles
P249: Average access time:
P250: 97% hits: 1 cycle + 0.03 * 100 cycles = 4 cycles
P251: 99% hits: 1 cycle * 0.01 * 100 cycles = 2 cycles
P252: Using miss rate instead of hit rate is more transparent
P266: Linkers
P268: Remember that a C program is compiled as:
P269: Preprocessor: Removes comments and expands macros. Outputs .i file
P270: Compiler: Turns preprocessed C code into assembly code. Outputs .s file
P271: Assembler: Turns assembly into machine code. Outputs .o, a relocatable object file
P272: Shared object files (.so): Special type of relocatable object file that can be loaded into memory and linked dynamically, at either load time or runtime
P273: Both .o and .so files contain a symbol table that’s actually an array of structs per symbol, each struct containing the symbol’s name, size and memory location.
P274: More on symbols soon...
P275: Linker: Combines all necessary object files (like whatever was from stdio.c) into executable object file a.out (default name)
P276: Linker performs symbol resolution, using symbol tables from the .o files, then afterwards it performs relocation
P278: Executable and Linkable Format (ELF): Standard format for .o, executables and .so

P307: Symbol Resolution
P309: There are 3 types of linker symbols:
P310: Global: Defined by module p and can be referenced by other modules
P311: Not static functions and global variables
P312: External: Global symbols referenced by module q but defined by p
P313: Variables use the extern keyword
P314: Local: Defined and referenced exclusively by module p. Nothing else
P315: static functions and global variables
P316: Local variables (defined inside functions without static) are NOT linker symbols
P317: The linker simply ignores them (ignores stack and heap)
P321: Symbol resolution: Linker uses the symbol table, found in the .o files, to resolve references
P322: The linker associates each symbol reference with exactly one symbol definition (not declaration)
P323: val, a, i, n and s are ignored (local variables)
P325: The unique case of static local variables:
P327: First call of g(): returns 2. Second call of g(): 3. Defined once, cannot be redefined
P329: Strong vs weak symbols
P331: Weak: Uninitialized global variables
P332: Strong: Everything else (functions and initialized globals)
P333: int foo = 5; // Strong
P334: int bar;  // Weak
P335: void q() {}  // Strong
P336: The rules concerning this:
P337: Rule 1: Multiple strong symbols with the same name are not allowed. Throw linker error
P338: Rule 2: References to the strong symbol (if any) are preferred over any weak symbols
P339: Rule 3: If there are multiple weak symbols, pick an arbitrary one

P346: Takeaway: Don’t use global variables
P347: If you must, use static
P348: If it must be used elsewhere, make it strong
P349: Use extern if you reference an external global variable
P356: Relocation
P358: Relocation: Linker merges separate code and data sections into a single section
P359: Relocates symbols from their relative addresses in the .o files to their final absolute memory addresses in the executable
P360: Compiler and assembler assume that memory addresses start at 0
P361: Updates all references to these symbols to reflect their new positions
